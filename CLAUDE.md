# За кулисами правды — онлайн-часть детективной игры

Ты собираешь интернет-часть настольной детективной игры «дело в конверте». Игроки (одна команда, 3–8 взрослых) получают бумажную папку дела и запечатанные конверты 2–4. Сайт ведёт игру сам, без ведущего: проверяет ответы, говорит, какой конверт открыть, выдаёт результаты экспертиз и подсказки, считает баллы и показывает развязку. Плюс набор вымышленных веб-страниц (соцсети, новостной портал, облако, справочник), на которые игроки попадают по QR-кодам из бумажных материалов.

Сначала игра делается для семьи (настоящие имена родственников), потом, возможно, продаётся: тогда меняется только контент, движок остаётся.

## Источники правды

Читай в таком порядке, прежде чем менять что-то существенное:

1. `docs/01-game-spec.md` — правила игры: этапы, типы вопросов, попытки, баллы, подсказки, экспертизы, финал.
2. `docs/02-architecture.md` — статический сайт, нормализация ответов, криптосхема, хранение прогресса, модель угроз.
3. `docs/03-content-format.md` — схемы файлов в `content/`, шаблоны и склонение имён.
4. `docs/04-pages.md` — что на каждой странице.
5. `docs/05-design.md` — визуальный язык.
6. `docs/06-testing.md` — проверки и критерии готовности.

Сюжет, ответы и тексты живут только в `content/`. Не придумывай сюжетные факты, ответы, улики и имена. Если для кода не хватает контента — поставь явную заглушку `TODO(content): …` и упомяни её в отчёте.

Если документы противоречат друг другу или коду — остановись и спроси, не выбирай сам.

## Жёсткие правила

- **Никакого сервера.** Результат сборки — папка статических файлов `dist/`, которую можно положить на любой статический хостинг. Никаких запросов к внешним API во время игры, никаких CDN: шрифты, скрипты и стили лежат в `dist/`.
- **Ни одного открытого ответа в `dist/`.** Ответы, тексты следующих этапов, результаты экспертиз, развязка и закрытые страницы попадают в `dist/` только зашифрованными (см. `docs/02-architecture.md`). Сборка обязана проверять это сама (leak scan) и падать при утечке.
- **Нормализация и криптография реализованы дважды** — в Python (сборка) и в JS (браузер) — и обязаны давать побайтно одинаковый результат. Общие тестовые векторы лежат в `tests/vectors/`; любое изменение логики сопровождается обновлением векторов и тестов с обеих сторон.
- **Только вымышленные бренды.** Никаких логотипов, названий, гербов и узнаваемого фирменного стиля реальных компаний и госорганов (VK, Instagram, Telegram, Яндекс, Госуслуги, СК РФ, МВД и т.п.). Страницы должны выглядеть правдоподобно, но принадлежать вымышленным сервисам из `content/world.yaml`.
- **Все параметры — в конфиге.** Баллы, штрафы, число итераций, пороги рангов, тексты — в `content/`. В коде нет «магических» чисел и строк сюжета.
- **Все тексты интерфейса — на русском.** Идентификаторы в коде — на английском, комментарии можно по-русски.
- **Репозиторий приватный.** В `content/` лежат ответы. Публикуется только `dist/`.
- **Кодировки и Windows.** Любое чтение и запись файлов в Python — с `encoding="utf-8"`; в начале `engine/__main__.py` — `sys.stdout.reconfigure(encoding="utf-8")` и то же для `stderr`. Пути — через `pathlib`. Хеши от файлов — по канонической форме (JSON с сортировкой ключей, `\n`), а не по сырым байтам: Git может менять переводы строк.

## Стек

- Сборка: Python 3.11+, `PyYAML`, `Jinja2`, `pydantic` (валидация контента), `cryptography`, `segno` (QR), `pytrovich` (склонение ФИО).
- Фронтенд: чистый JavaScript (ES-модули, без фреймворков и бандлера), Web Crypto API, CSS без препроцессоров.
- Тесты: `pytest`; Node.js 22 LTS для кросс-языковых тестов криптографии (`node:test`, встроенный `globalThis.crypto.subtle`); Playwright для сквозных тестов.
- Python-зависимости для печати и импорта: `playwright` (Python-версия — PDF и PNG из HTML, без вызова `npx` из Python), `markdown-it-py` (Markdown → HTML), `python-frontmatter` (front matter документов), `openpyxl` (чтение таблицы персонажей).
- Шрифты: PT Sans и PT Serif — свободная лицензия OFL, файлы кладутся в репозиторий.

## Команды

Кросс-платформенно, через модуль `engine` (без Makefile):

```
python -m engine build        # собрать dist/ из content/ + site/
python -m engine check        # самопроверка: прохождение правильными ответами + leak scan
python -m engine serve        # локальный сервер dist/ на http://localhost:8000
python -m engine qr           # QR-коды для печати → print/qr/
python -m engine answers      # «Аварийный конверт» с ответами → print/answers.pdf
python -m engine chatshot     # «скриншоты» переписок для печати → print/chats/
python -m engine paper        # бумажные документы конвертов (content/paper/) → print/paper/*.pdf
python -m engine names        # таблица падежных форм всех персонажей
python -m engine import-cast <xlsx>  # имена из таблицы персонажей → content/characters.yaml
python -m engine release      # build --release + check --release + архив dist
python -m engine vectors      # тестовые векторы криптографии → tests/vectors/crypto.json
python -m engine dump-answers # ответы и варианты (отрендеренные) → tests/.answers.json для JS/e2e-тестов
python -m engine rotate-salts --yes  # пересоздать соли и ключи страниц (после — перепечатать QR)
python -m pytest              # тесты Python
npm run test:js               # тесты JS (= node --test "tests/js/*.test.mjs")
npx playwright test           # сквозные тесты (после build)
```

## Структура

```
content/          сюжет, ответы, тексты (приватно) — см. docs/03
content/paper/    тексты бумажных документов конвертов — только печать, в dist/ не попадают
engine/salts.lock.json  соли и ключи страниц — коммитится, не пересоздаётся
media/            исходные фото, аудио, видео
engine/           сборщик на Python
site/
  templates/      Jinja2-шаблоны страниц
  assets/js/core/ normalize.js, crypto.js, state.js — общие модули
  assets/js/app/  главный экран, лаборатория, финал
  assets/js/pages/ скрипты вымышленных страниц
  assets/css/
  assets/fonts/
tests/            pytest, node-тесты, tests/vectors/, tests/e2e/
print/            файлы для печати (QR, аварийный конверт, скриншоты переписок)
dist/             результат сборки — не редактировать руками
docs/             спецификации
prompts/          пошаговые задания для разработки
```

## Сценарист и разработчик

Сюжет ведёт сценарист (Claude в чате автора), код — ты. Сценарист присылает изменения пулл-реквестами:
- ветка `story/<дата>-<тема>`, заголовок PR и коммиты начинаются с `story:`; в описании PR — что изменилось и что сделать тебе;
- каждый такой PR добавляет запись в `docs/STORY-CHANGES.md` (раздел с датой и пометкой «от сценариста») и при необходимости обновляет `docs/SCENARIO.md` и `content/`;
- `docs/SCENARIO.md` — полный технический сценарий, источник правды по сюжету. Раздел «Синхронизация с репозиторием» в его конце важнее таблиц выше;
- **перед началом любой работы:** `git pull`, затем `gh pr list --search "story:" --state open`. Открытые PR сценариста влей в основную ветку (если есть конфликт с твоими правками — разреши его, сохранив обе стороны), прочитай новые записи «от сценариста» в `docs/STORY-CHANGES.md` и выполни раздел «Для разработчика» в них. После — `build`, `check`, тесты;
- если сюжетная правка ломает код или противоречит другим документам — не выбирай сам: допиши вопрос в конец записи в `STORY-CHANGES.md` под заголовком «Вопрос к сценаристу» и сообщи автору;
- свои сюжетные правки (как раньше) тоже записывай в `STORY-CHANGES.md` — сценарист читает журнал при каждой синхронизации.

## Как работать

- Большую задачу начинай с короткого плана и списка файлов, которые затронешь.
- Делай маленькими шагами: после каждого шага — тесты зелёные, `python -m engine check` проходит.
- Не удаляй и не переписывай `content/` без прямой просьбы. Исправления формата контента предлагай отдельным сообщением.
- В конце каждой задачи пиши отчёт: что сделано, как проверить руками, какие `TODO(content)` и открытые вопросы остались.

## Определение готовности

Задача готова, когда:
- `python -m pytest`, `npm run test:js` и `python -m engine check` проходят;
- в `dist/` нет открытых ответов (leak scan зелёный);
- страница работает на ширине 360 px и на ноутбуке, без горизонтальной прокрутки;
- поведение совпадает с `docs/`; расхождения описаны в отчёте.
