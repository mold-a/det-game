# 02. Архитектура, нормализация и шифрование

## 1. Общая схема

```
content/*.yaml + content/pages + content/documents + media/
        │
        ▼  python -m engine build
  ┌──────────────────────────────────────────────┐
  │ 1. загрузка и валидация (pydantic)            │
  │ 2. подстановка имён, склонение (Jinja2)       │
  │ 3. нормализация вариантов ответов             │
  │ 4. записи-проверки ответов, ключи этапов      │
  │ 5. шифрование пакетов, экспертиз, страниц     │
  │ 6. рендер HTML, копирование ассетов           │
  │ 7. самопроверка и leak scan                   │
  └──────────────────────────────────────────────┘
        │
        ▼
      dist/  ← статические файлы, без открытых ответов
```

Браузер получает зашифрованные пакеты и расшифровывает их ключами, которые выводятся из правильных ответов команды. Сервер не участвует.

**Защищённый контекст.** Web Crypto (`crypto.subtle`) работает только по HTTPS или на `localhost`. Открытие `dist/index.html` через `file://` и проверка с телефона по `http://192.168.x.x` работать не будут — для телефона нужен HTTPS (выкладка на хостинг или туннель). Сайт должен это распознавать и показывать понятное сообщение, а не падать.

## 2. Нормализация ответов

Реализуется одинаково в `engine/normalize.py` и `site/assets/js/core/normalize.js`. Тестовые векторы: `tests/vectors/normalize.json` (вход, тип, ожидаемый выход или `null` для невалидного) — общие для обеих реализаций, не меньше 60 случаев, включая кириллицу, «ё», лишние пробелы, знаки препинания, эмодзи, латиницу, пустые строки.

**base(s):**
1. Unicode NFC.
2. В нижний регистр (`str.lower()` / `toLowerCase()`).
3. «ё» → «е».
4. Диакритика и прочие комбинируемые знаки (категория M*, например ударение U+0301) удаляются. Каждый остальной символ, который не буква (L*) и не цифра (N*), заменяется пробелом. Подчёркивание — тоже пробел.
5. Пробелы схлопываются, края обрезаются.

| Тип | Правило | Пример |
|---|---|---|
| `text` | `base(s)` | « Бронхиальная  астма! » → `бронхиальная астма` |
| `password` | `base(s)` без пробелов | «Маскарад-1835» → `маскарад1835` |
| `time` | Группы цифр: одна группа из 3–4 цифр → `HMM`/`HHMM`; две группы → `H`, `M`. Проверка 0–23 и 0–59. Выход `HH:MM` | «08.15», «815», «8 ч 15» → `08:15`; «25:70» → невалидно |
| `date` | Группы цифр: 2 группы → день, месяц, год из `settings.default_year`; 3 группы → день, месяц, год (2 цифры → 20YY). Проверка календаря. Выход `YYYY-MM-DD` | «05.03» → `2026-03-05` |
| `number` | Все цифры подряд, без ведущих нулей (`0` остаётся) | «касса №2» → `2` |
| `choice`, `person`, `document` | ID как есть (латиница, цифры, `-`, `_`) | `zavyalov` |
| `multi`, `persons` | Уникальные ID, сортировка по кодовым точкам, через `,`. Пусто → невалидно | `gromov,oleg,stas` |
| `order` | ID в порядке пользователя через `,` | `e1,e2,…,e8` |

Невалидный ввод не считается попыткой — интерфейс показывает подсказку по формату.

**Примеры в интерфейсе** (плейсхолдеры, подсказки формата) — только нейтральные значения, которые не совпадают ни с одним ответом: например «08:15», «05.03». Leak scan их проверяет.

## 2а. Распознавание объекта лаборатории

Игрок вводит объект исследования свободным текстом («Укажите предмет так, как он назван в описи изъятого»). Из текста получается `object_id`; дальше всё как в §3.6. Алгоритм реализован одинаково в `engine/labmatch.py` (`lab_tokens`, `resolve_object`) и `site/assets/js/core/labmatch.js` (`labTokens`, `resolveObject`); общие векторы — `tests/vectors/lab-match.json` (генерирует `python -m engine vectors`, ожидания в нём написаны руками и сверяются с кодом при генерации).

**Токены.** `norm(s)` — это `normalize("text", s)` из §2 (NFC, нижний регистр, «ё»→«е», не буквы и не цифры → пробел, пробелы схлопнуты); пустой результат — `""`. `lab_tokens(s) = norm(s).split(" ")`, пустая строка → `[]`.

**Алиасы.** У объекта в `expertise.yaml` — `aliases: [строка…]`; каждая строка — одна или несколько **основ** через пробел (`"таблетниц"`, `"бутыл вод"`). Сборка применяет к ним `norm`, в `dist/` уходят уже нормализованные. Основа `s` подходит токену `t`, если `t` начинается с `s`. Название объекта (`title`) — тоже алиас: его основы — все токены названия длиной не меньше 3 символов, кроме служебных слов (`для при над под без или что как это про через между` — один и тот же список в `TITLE_STOPWORDS` обеих реализаций): «Бутылка воды из гримёрки № 4» → `бутылка`, `воды`, `гримерки`; «Футляр для очков» → `футляр`, `очков`.

**Совпадение алиаса.** Основы идут по порядку; каждая занимает самый ранний ещё не занятый токен, к которому подходит (поэтому повтор основы требует двух токенов, а порядок основ в вводе не важен). Не нашлось токена хотя бы одной основе — алиас не совпал. Иначе `pos` — минимальный индекс занятого токена, `score` — сумма длин основ (в символах Unicode, не в единицах UTF-16).

**Выбор объекта.** Лучшее совпадение объекта — минимум `(pos, -score)` по его алиасам. Из доступных на этапе объектов (`from_stage ≤` последнего открытого этапа) с совпадением берутся те, у кого лучший ключ наименьший:
- один → `{status: "ok", id}`;
- несколько → `{status: "ambiguous", ids: […]}` — в порядке объектов в `expertise.yaml`;
- ни одного (в том числе пустой ввод) → `{status: "none"}`.

Так «ключи из кармана пальто» → «ключи» (`pos` 0 раньше `pos` 3 у «пальто»). Постановка `none` и `ambiguous` — без штрафа; штраф — только за распознанный объект с запросом без записи (docs/01).

**Проверки сборки** (`build` и `check`; ошибка останавливает сборку, сообщение — файл, путь до поля, причина):
- каждая основа алиаса не короче 3 символов после `norm`, алиас не пуст;
- у разных объектов нет одинаковых алиасов (основы сравниваются как множество);
- `title` каждого объекта распознаётся как сам объект на каждом этапе, где он доступен;
- **правило оснований:** если объект доступен раньше этапа результата (`from_stage < stage`), то каждое основание этого результата — документ этапа `stage`. Иначе один и тот же запрос на раннем этапе дал бы «ничего не выявила», а позже — заключение, что противоречит «повтор той же комбинации не штрафуется повторно»;
- предупреждение (не ошибка): два объекта имеют общую основу длиной ≤ 4 символов.

`python -m engine check` дополнительно проходит лабораторию как браузер: берёт название объекта из расшифрованных пакетов, распознаёт его через `resolve_object` среди объектов пакетов `1…N` и выводит ключ экспертизы уже по найденному `id`.

## 3. Криптография

### 3.1 Примитивы

| Что | Алгоритм | Параметры |
|---|---|---|
| Ключ из ответа или пароля | PBKDF2-HMAC-SHA256 | 32 байта; итерации из `settings.crypto` |
| Производный ключ (ключ пакета, экспертизы, развязка) | HKDF-SHA256 | 32 байта; соль — 32 нулевых байта явно с обеих сторон |
| Шифрование | AES-256-GCM | nonce 12 случайных байт, тег 128 бит, AAD обязателен |
| Кодирование | base64url без `=` | — |
| Строки → байты | UTF-8 | — |

Контейнер зашифрованных данных (файл или поле JSON):

```json
{ "v": 1, "alg": "A256GCM", "aad": "pack/2", "n": "<nonce>", "c": "<ciphertext+tag>" }
```

`aad` хранится открыто и передаётся в расшифровку — он защищает от подмены одного контейнера другим.

### 3.2 Соли и постоянные ключи — `engine/salts.lock.json`

Генерируется при первой сборке, коммитится в приватный репозиторий, **никогда не пересоздаётся автоматически**. Содержит:
- соль на каждую проверяемую единицу (вопрос или поле формы) — 16 байт;
- соль на каждый этап и стартовую соль;
- соль облака;
- ключи закрытых страниц (32 байта) — они напечатаны в QR-кодах, поэтому должны переживать пересборку.

Новая единица → новая соль дописывается. Удалённая → соль остаётся (не мешает). Команда `python -m engine rotate-salts --yes` пересоздаёт всё (после неё QR-коды нужно перепечатать — предупредить).

### 3.3 Проверка ответа (без раскрытия ответа)

Для каждой единицы `u` (путь вида `s1.q1.time`):
- `K(x) = PBKDF2(UTF8("detgame/answer/v1|" + u.path + "|" + x), salt_u, ITER_ANSWER)`.
- Для каждого допустимого нормализованного варианта `v`: запись = `AESGCM(K(v)).encrypt(nonce, UTF8(JSON {"c": canonical, "p": padding}), aad = UTF8("ans/" + u.path))`.
- **Выравнивание длины.** Без него длина контейнера (`len(c) − 16`) выдаёт длину канона, а у `choice`/`person` — часто и сам ID. Поэтому `p` — строка пробелов такой длины, чтобы открытый текст (канонический JSON: ключи `c`, `p` по порядку, без пробелов, UTF-8) занимал ровно `L` байт: `L` кратно 64 и не меньше 128; если канон длиннее, `L` — следующее кратное 64. Клиент читает только поле `c`; `p` игнорируется.
- Записи дополняются случайными до `settings.crypto.entries_pad` (по умолчанию 8) — шифротекст той же длины `L + 16`, что у настоящих (все записи единицы одной длины), — и перемешиваются.
- Клиент: нормализует ввод, считает `K(ввод)` один раз, пробует расшифровать каждую запись. Успех → ответ верный, получен канонический вид. Иначе — неверный.

Допуски (например, время ±2 минуты) сборщик раскрывает в отдельные варианты. Синонимы перечислены в `content/stages.yaml`.

### 3.4 Ключи этапов

- `K1 = PBKDF2(UTF8("detgame/stage/v1|start"), salt_start, ITER_STAGE)` — стартовый ключ: выводится из публичных данных, это не защита, а маскировка, чтобы в `dist/` не было открытых ответов этапа 1.
- Для этапов N = 1…3: обязательные единицы `U_N` в порядке из `content/` (поля формы раскрываются по порядку).
- `secret_N = "detgame/stage/v1|" + N + "\x1f" + "\x1f".join(u.path + "=" + canon_u for u in U_N)`.
- `K_{N+1} = PBKDF2(UTF8(secret_N), salt_stage_N, ITER_STAGE)`.
- `K_N` — секрет этапа: хранится в прогрессе как байты и напрямую не шифрует ничего. Из него через HKDF выводятся ключ пакета, ключи экспертиз и ключ развязки.

### 3.5 Пакеты этапов — `dist/data/pack-N.json`

Пакет N шифруется ключом `HKDF(K_N, info = "detgame/pack/v1|" + N)`, `aad = "pack/N"`. Внутри:
- вводное письмо этапа, сообщение про конверт;
- вопросы (тексты, варианты, тип, флаг обязательный/бонус/финал) с записями-проверками и солями единиц;
- подсказки этого этапа;
- соль этапа `salt_stage_N` (нужна для вывода следующего ключа);
- список документов этапа (ID, название, тип: бумага / онлайн / экспертиза);
- `LabCatalog` — каталог лаборатории и записи экспертиз, которые открываются на этом этапе:
  - `types[]` — только в пакете первого этапа: `{id, title, ord, description}`;
  - `objects[]` — предметы описи, у которых `from_stage = N`: `{id, title, ord, params[], aliases[], ref}`; `aliases` — нормализованные основы (§2а), `ref` — ссылка на опись («1-09, поз. 17.3») или `null`. Алиасы поздних предметов открываются вместе с их этапом; пакет этапа 1 открыт стартовым ключом — там только предметы этапа 1;
  - `entries[]` — записи экспертиз (§3.6);
- `pages[]` — профили закрытых этапов этого этапа (§3.10): `{slug, type, key, name, position}`; `key` — base64url ключа страницы `K_p` (тот же, что в QR), `name` и `position` — строки поиска «Круга» (`position` — должность профиля `social`, иначе `null`). Пустой список, если таких профилей нет.

`dist/data/public.json` — открытые данные: название, `game_id`, число этапов, стартовая соль, итерации, `entries_pad`, баллы (`points`), штрафы, цены подсказок и порог автоподсказки, ранги, `default_year`, `saltsId` (SHA-256 канонического JSON `salts.lock.json` — сортировка ключей, без пробелов, UTF-8), `buildId`. Ничего сюжетного.

### 3.6 Экспертизы

Запись экспертизы, открывающейся на этапе N, для каждого допустимого основания `b` и каждого варианта параметров `p`:
- `key = HKDF(K_N, info = UTF8("detgame/lab/v1|" + object + "|" + type + "|" + b + "|" + p))`, где `p` — нормализованные параметры через `|` в порядке из конфига (пусто, если параметров нет).
- Содержимое: `{"doc": "<id>", "title": "...", "html": "<отрендеренный документ>", "media": [...]}`, `aad = "lab"`.
- Записи этапа дополняются до `entries_pad` и перемешиваются.
- `object` в ключе — `id`, найденный по тексту игрока (§2а), а не сам текст. Нераспознанный и неоднозначный ввод ключей не выводит вовсе.
- Клиент на **каждый** запрос заново перебирает открытые этапы n ≤ текущего, выводит ключ из `K_n` и пробует записи этапа n. Если совпало на нескольких этапах — берётся результат самого позднего. Кеш прошлых запросов нужен только чтобы не штрафовать повторно, но не заменяет проверку: запрос, отклонённый на этапе 1, на этапе 3 может дать результат.
- Медиа результатов (например, стоп-кадр 4-08) шифруются: у каждого файла свой случайный ключ, он хранится внутри зашифрованной записи экспертизы. Файл — `dist/m/<hash>.bin`.

### 3.7 Финал и развязка

- Финальные вопросы — в пакете 4, проверка как в §3.3, одна попытка.
- Развязка — `dist/data/finale.json`, ключ `HKDF(K_4, info = "detgame/finale/v1")`, `aad = "finale"`. Показывается только после отправки всех финальных ответов.
- Внутри развязки — поле `answers`: путь каждой единицы → текст верного ответа для экрана разбора. Без него клиент не смог бы показать верный ответ на проваленный бонус или финальный вопрос.

### 3.8 Закрытые страницы (по QR)

- У каждой закрытой страницы постоянный ключ `K_p` из `salts.lock.json`.
- QR ведёт на `https://<домен>/p/<slug>/#k=<base64url(K_p)>`. Фрагмент после `#` браузер не отправляет на хостинг.
- `dist/p/<slug>/index.html` — пустая оболочка со скриптом; содержимое — `dist/p/<slug>/payload.json`, `aad = "page/<slug>"`.
- Медиа закрытых страниц шифруются тем же ключом (`aad = "media/<hash>"`), лежат как `dist/m/<hash>.bin` и показываются через Blob URL.
- После чтения ключа страница убирает фрагмент из адресной строки (`history.replaceState`) и сохраняет ключ в `sessionStorage` под `detgame:page:<slug>` — чтобы перезагрузка и выгрузка вкладки на iOS не превращались в «Ссылка повреждена».
- Нет ключа или он неверный → «Ссылка повреждена. Отсканируйте QR-код ещё раз».

### 3.9 Облако

- Ключ `PBKDF2(UTF8("detgame/cloud/v1|" + password(ввод)), salt_cloud, ITER_STAGE)`; пароль — из записки в конверте 4.
- `dist/p/cloud/payload.json` = `{"salt": "<salt_cloud>", "iter": ITER_STAGE, "box": <контейнер с aad = "page/cloud">}` — соль и итерации открыты, это нормально.

### 3.10 Профили закрытых этапов («Круг», «Кадр»)

Профиль `type: social` или `photo` с `stage: N ≥ 2` и `locked: true` — закрытая страница §3.8 со своим `K_p`, но попадают на неё не по QR, а по ссылкам, которые есть и на открытых страницах (друзья, авторы комментариев, поиск «Круга», карточки сайта театра).

- **Сборка.** Ссылка на такой профиль со страницы A, если A открыта или её этап меньше N, рендерится как ссылка на заглушку: `href="/p/<stub>/#to=<slug>" data-gate="<slug>"` (у закрытой заглушки — `#k=<ключ заглушки>&to=<slug>`). Заглушка — поле `stub` профиля, у «Круга» по умолчанию `krug-private`; у «Кадра» `stub` обязателен (`photo_stub`). Ключ профиля в открытый файл не попадает. Со страниц этапа ≥ N — обычная ссылка с ключом (§3.8).
- **Пакет этапа N** содержит ключи этих профилей и строки поиска (`pages[]`, §3.5). Пакет 1 открыт публичным ключом — профилей этапа 1 в этом механизме нет.
- **Браузер** (`core/gate.js`, `pages/gate.js`): на любой вымышленной странице, где есть `a[data-gate]`, поиск «Круга» или фрагмент `#to=`, читает прогресс этого сайта (`localStorage["detgame:<gameId>"]`, тот же источник, §4), при совпадении `saltsId` расшифровывает пакеты открытых этапов (HKDF от `K_n`, как главный экран), и: ссылки с известным slug получают настоящий адрес `/p/<slug>/#k=<K_p>`; заглушка, открытая с `#to=<slug>`, сразу переходит на профиль; поиск «Круга» добавляет профили из пакетов (и меняет «Профиль закрыт» на должность). Расшифрованный список кешируется в `sessionStorage["detgame:gate"]` с подписью `saltsId|buildId|этапы`. Нет прогресса (телефон, который сканирует QR, а не играет), другие соли, ошибка сети — ссылки остаются заглушками.
- **Открытый индекс поиска** на `krug`: открытые профили этапа 1 (имя, должность, ссылка) и профили закрытых этапов, на которые уже ведут ссылки-заглушки с открытых страниц (имя и так видно) — только имя, «Профиль закрыт», ссылка на заглушку. Остальные профили этапа N появляются в поиске только из пакета этапа N.
- **Темп или тайна.** `gate: pacing` в `page.yaml` — профиль закрыт ради темпа (не перегружать конверт 1 сетью из 15 профилей), а не ради тайны: он шифруется и до этапа недоступен, но его текст leak scan секретом не считает (те же люди комментируют открытые страницы). Без `gate: pacing` закрытый профиль — обычная закрытая страница: его тексты — секрет (§5а).
- **Проверки** (`build`, `check`): заглушка существует и сама подчиняется правилам ссылок §4.1 docs/04; профиль `social`/`photo` с `stage ≥ 2` без `locked: true` — ошибка; ссылка с открытой страницы на закрытую страницу другого типа — ошибка, как раньше; в готовом HTML `#to=` стоит только там, где заглушка нужна, и ведёт на заглушку этого профиля; ключ страницы этапа ≥ 2 не встречается ни в одном текстовом файле `dist/` и в открытом тексте pack-1 (ошибка check «ключ страницы … лежит открытым»); `pages[]` пакета N — ровно профили этапа N с ключами из QR.

## 4. Прогресс — `localStorage`

Ключ `detgame:<gameId>`. Значение — JSON:

```json
{
  "v": 1,
  "saltsId": "…",
  "buildId": "…",
  "team": "…",
  "startedAt": "ISO-8601",
  "stage": 2,
  "finished": false,
  "keys": { "1": "…", "2": "…" },
  "units": { "s1.q1": { "status": "solved", "canon": { "time": "21:18" } } },
  "wrong": { "s1.q2": ["<sha256 нормализованного неверного ввода>"] },
  "hints": { "s1.q1": 2 },
  "lab": { "done": { "<fp>": "2-01" }, "rejected": ["<fp>"] },
  "docs": ["2-01"],
  "final": { "index": 0, "answers": {} },
  "log": [ { "t": "ISO-8601", "d": -5, "r": "wrong:s1.q2" } ]
}
```

- Счёт = сумма `log[].d`. Других источников счёта нет.
- При загрузке: `saltsId` не совпал или сохранённый ключ не расшифровывает пакет → прогресс несовместим, предложить начать заново.
- Экспорт и импорт — тот же JSON в файле.
- Все обращения к `localStorage` — в `try/catch`; если хранилище недоступно, игра работает в памяти и предупреждает, что прогресс не сохранится.
- `/`, `/lab/` и `/final/` могут быть открыты в разных вкладках: перед каждой записью состояние перечитывается и изменения сливаются; на событие `storage` интерфейс обновляется.

## 4а. Медиа

- Открытые медиа (портреты, фото открытых страниц) копируются как `dist/m/<sha256-префикс>.<ext>`.
- Медиа, на которые ссылается **только** зашифрованный контент (пакеты, экспертизы, развязка, закрытые страницы), шифруются: `dist/m/<hash>.bin` = `nonce (12 байт) ‖ ciphertext ‖ tag (16 байт)`, `aad = "media/<hash>"`, ключ хранится в том зашифрованном объекте, который на файл ссылается. В браузере — Blob URL с исходным MIME-типом из этого объекта. Ключ новый в каждой сборке, а имя файла то же, поэтому ссылка на файл несёт версию по его байтам: `/m/<hash>.bin?v=…` (FORMATS §5) — иначе кеш `immutable` отдал бы старую копию, которую новый ключ не открывает.
- `check` падает, если медиа, используемое только зашифрованным контентом, лежит в `dist/` открытым.

### 5а. Leak scan: что секрет, что публично

Иголки бывают двух видов (`engine/leakscan.py`, `engine/check.py: leak_needles`, список проверок — docs/06 §3.7): **значения** (ответы, параметры экспертиз, `leak_watchlist`, пароль, названия документов этапов 2–N) и **шинглы** — все четвёрки токенов `base()` секретных текстов.

**Секрет** — то, что в `dist/` зашифровано или вовсе не публикуется: пакеты этапов 2–N, подсказки всех этапов, экспертизы, развязка, закрытые страницы (кроме `gate: pacing`, §3.10: у них секрет — только ключ) и бумага конвертов (`content/paper/`). Текст закрытого профиля «Круга»/«Кадра» берётся по блокам вёрстки: шинглы через границы блоков шаблона («Комментарии 1» + имя автора) — обвязка, а не секрет. Шинглы секретов ищутся во **всех** файлах `dist/`, включая открытые страницы (`locked: false`), и в открытом тексте `pack-1` (кроме иголок этапа 1).

**Что не отбеливает секрет.** Проза открытых страниц и открытого текста этапа 1 *не* делает свои шинглы «публичными»: если фраза закрытого текста скопирована на открытую страницу, это утечка. Иначе любая вставка из экспертизы в пост открытой страницы проходила бы незамеченной. Исключения (шингл не иголка) — только три:
1. **Оболочка и наименования** — статический текст шаблонов `site/templates`, строки `texts.js`, название игры, бренды мира, шапка и номер дела, заглушки сборщика, бренд и аккаунт страниц, тексты подвала сервисов (`pages/_brands.yaml`), названия объектов каталога pack-1 (с алиасами и ссылками на опись), названия документов этапа 1, названия и описания видов экспертиз. Подписи подвала «О сервисе · Правила · Помощь» (`UI_LABEL_WORDS`) тоже служебные.
2. **Явный список законных повторов** — `settings.leak_public_ok`: фразы (с шаблонами `{{ }}`), которые законно стоят и в открытом, и в закрытом тексте: названия организаций и учреждений, должности и подписи, адреса, афиша, служебные формулы. Шингл фразы не считается иголкой. Туда не попадают факты и улики. Сборка падает на любом пересечении вне списка: ошибка называет файл, шингл и источник секрета, и автор решает — переписать открытый текст или внести фразу в список.
3. **Бумага конверта 1** (печатная копия открытого мира этапа 1) вправе цитировать открытые страницы; бумага конвертов 2–N открытыми страницами не отбеливается (её законные совпадения — тоже `leak_public_ok`). Страницы приложения и `public.json` бумага цитировать вправе всегда.

Значения ответов этапа 1 и открытые факты (например, геометка на открытой странице) утечкой не считаются: этап 1 открыт по замыслу, его иголки в `pack-1` и на открытых страницах не ищутся. Общий порядок такой: сначала решает список иголок-значений, затем шинглы секретов; всё, что не секрет по списку выше, не проверяется. Тест — `tests/test_leak_open_pages.py` (вставка из закрытого текста в открытую страницу ловится, бренд — нет).

## 6. Модель угроз — честно

**Защищает от:** чтения ответов, текстов следующих этапов и закрытых страниц через «Просмотр кода», вкладку «Сеть» или файлы на хостинге; случайных спойлеров; поисковиков.

**`gate: pacing`** (§3.10) не защищает от спойлеров вовсе: тексты таких профилей могут совпадать с открытыми страницами, а адрес профиля открывается любому, у кого в браузере есть прогресс с ключом этапа. Это защита от перегруза (сеть раскрывается по конвертам), а не от подглядывания.

**Не защищает от:** программиста, который напишет скрипт перебора. У вопросов с выбором мало вариантов, каждый вопрос проверяется отдельно, а ключ этапа 1 выводится из публичных данных. Счёт можно подправить в `localStorage`. Для домашней игры и коробочного продукта этого достаточно; утверждать в интерфейсе или документах, что ответы «невозможно взломать», нельзя.

**Время проверки.** Итерации PBKDF2 подбираются так, чтобы одна проверка занимала не больше ~0,4 с на телефоне среднего уровня. Значения по умолчанию: `ITER_ANSWER = 150 000`, `ITER_STAGE = 300 000`. Замерить в P08 и при необходимости снизить в `settings.yaml`.
